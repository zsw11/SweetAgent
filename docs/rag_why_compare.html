为什么用 RAG？——三种"让 LLM 知道私域知识"的方案对比
RAG / 微调 / 长上下文 | 本项目选型依据（示意）
RAG（本项目）✅
做法：按需检索相关片段 → 注入 prompt
优点
· 知识实时更新（改库即可，SOP 从 v2.4 升 v3.2 不用重训）
· 答案可溯源（命中片段带 title/similarity/method）
· 成本低（只注入 top-5 块 ≈ 1750 token）
· 不改模型权重，零训练
缺点
· 上限取决于检索质量（召不回 → 答不好）
本项目选择：知识高频迭代 + 要溯源 + 成本敏感 + 多部门隔离
微调 Fine-tuning
做法：用数据改模型权重，知识"焊死"进参数
优点
· 风格/行为固化（适合模仿特定口吻/格式）
· 推理时零检索依赖
缺点
· 贵：数据标注 + 训练 + 推理成本
· 更新慢：知识变了要重新训练
· 灾难性遗忘：新知识挤掉旧能力
· 无法溯源（知识在权重里，答了说不清依据）
适合：改说话方式/输出格式，不是喂知识
长上下文 Long-context
做法：把全部知识塞进一次 prompt
优点
· 实现最简单
· 知识量小时效果好
缺点
· token 成本线性爆炸（11 篇全塞 ≈ 2.3 万 token/次）
· 噪声稀释：无关片段干扰判断
· Lost in the middle：模型对中部内容注意力衰减，关键知识被"淹没"
· 知识库大了窗口装不下
适合：小知识集、一次性资料
结论一句话：RAG 是"按需拿证据"——检索只取相关片段注入，兼顾更新快 / 可溯源 / 成本低；微调改的是"风格"不是"知识"，长上下文是"全量堆"注定稀释。本项目 11 篇知识高频迭代（SOP 版本号）、答案必须给依据、推理成本敏感 → 三者全中，选 RAG。
