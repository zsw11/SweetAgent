两个诚实回答：系统不知道改了内容 + version 是死字段
现状 vs 演进：version / 内容哈希该有的用法 | 示意
当前实现（真实代码）
① 系统不知道改了部分内容
ingest 只认 title：DELETE WHERE title=%s → 全量重建
不比较新旧内容，不看 version，无条件重灌
同 title 哪怕只差一个字 = 整篇重建；内容完全一样 = 也重建
② version 字段是"死字段"
INSERT 时写入（实测 doc#8='v2.4'、doc#10='v3.0'…）
但：幂等键 = 只有 title（不含 version）
检索 = 不区分版本（active 过滤只看 status）
→ version 只被"存了"，没有任何代码逻辑用它
演进 A · 内容哈希（让系统"知道改了内容"）
入库时对全文算 sha256 存 content_hash 列
重灌时：同 title + 同哈希 → 跳过（零成本幂等，不重建）
同 title + 不同哈希 → 更新（此时才真正"知道"内容变了）
演进 B · version 参与唯一键（让 version 活起来）
唯一键改为 (title, department, brand, market, version)
→ v2.4 / v3.0 并存，历史可查（审计"当时规定是什么"）
检索 ORDER BY version DESC LIMIT 1 取最新
变更时 version+1 → 版本演进有语义
当前 version 的价值只剩"展示"：seed_docs 标了 v2.4 等版本号，作为元数据给人看；逻辑上没有任何字段依赖它。 它是预留字段——表结构有前瞻，ingest 逻辑没跟上。
