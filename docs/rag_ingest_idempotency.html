为什么幂等？title 能保证什么、不能保证什么？
幂等 = 重跑安全 | title = 身份键（保证"同名不重复"）| content hash = 内容指纹（保证"同内容不重复"，进阶）| 示意
① 为什么幂等（重跑 N 次结果一致）
第 1 次跑：INSERT 文档A（1 行 documents + N 行 chunks + N 行 embeddings）
第 2 次跑：DELETE WHERE title='A'（CASCADE 自动清 chunks/embeddings）→ 重建
第 N 次跑：结果 = 和第一次完全一样的库状态
不幂等的后果：每跑一次多一份重复文档 → 检索重复召回、库膨胀、状态漂移（跑 3 次 = 3 份数据）
种子脚本本质是"数据迁移"——必须可重复执行、可回放、结果收敛
② title 是什么？能/不能保证什么？
title 从哪来（当前）：seed_docs.py 人工硬编码，业务命名规范 = 主题 + 类型
例：「跨境电商广告投放运营SOP」「库存预警与补货规则」——每篇文档的作者/维护者负责命名
✅ 能保证：同名不重复（重跑收敛）、删旧建新 = "更新"语义（同 title 内容变了 → 覆盖为新版）
❌ 不能保证"内容唯一"：
① title 改名 → 旧版残留 + 新版 = 重复（身份变了，幂等管不着）
② 两篇不同 title 内容重叠 → 检索重复召回
③ title 靠人工命名，本质是"信任约定"，不是机制
进阶（未做，可讲）：入库时对全文算 SHA-256 存库 → 重灌时对比：
同 title + 同哈希 → 跳过（零成本幂等）
同 title + 不同哈希 → 更新（版本演进）
不同 title + 同哈希 → 告警/去重（内容指纹兜住命名失误）
