Q1

任务怎么「暂停 → 恢复 → 续跑」？——一个系统里三层不同的断点机制

核心是第 1 层：LangGraph 的 interrupt() + PostgresSaver checkpoint + Command(resume)（质量门 human-in-the-loop）。另有两层：定时任务调度（DB 状态 + APScheduler + 重启重放）、多轮会话（thread_id 历史注入）。三者断点对象不同、哲学一致：断点落盘、应用层等待、无状态化恢复。

图 1｜quality_gate 的 human-in-the-loop 暂停 / 恢复主链路（示意）。代码：app/graph/main_graph.py:265（interrupt）、app/api/chat.py:196（resume）、app/memory/checkpoint.py（PostgresSaver）。
① 图执行断点（核心）
  • interrupt + checkpoint + Command(resume)
  • 恢复点 = State 快照（Postgres · thread_id 键）
  • 应对：进程崩溃 / 用户介入恢复

② 调度任务断点
  • DB 状态 + APScheduler 同步 + 重启重放
  • 恢复点 = 任务定义 + 启用状态
  • 应对：暂停 / 恢复 / 自动暂停 / 重启不丢

③ 多轮会话续跑
  • thread_id 历史 + 指代改写 + token 压缩
  • 恢复点 = 对话语义上下文
  • 应对：换轮次承接上文续聊

Q2

resume 恢复时，还要查数据库的对话上下文吗？——checkpoint 自足性

不需要。resume 恢复的是「图执行状态」，checkpoint 里的 GlobalState 快照对续跑自足；conversation_messages（历史表）只在「新开一轮」时才读。两条路径的数据流完全不同，见下图。

图 2｜两条路径数据流对比（示意）：左 = 新轮次入口（读历史表），右 = 恢复入口（只依赖 checkpoint）。代码：app/graph/main_graph.py:453（上下文构造）、app/api/chat.py:196-231（resume 零查询）。
! 结论：resume 恢复执行 = checkpoint 自足，无需再查数据库；conversation_messages 只在开新一轮时读。

缺口 1：暂停轮的草稿其实已写历史
  • decision 先把 current_stage 置「done」才轮到 quality_gate 中断
  • 中断返回时 stage 仍为 done，run_question 的「仅 done 才 append_turn」守卫挡不住
  • 草稿答案已入库（与注释意图不符，影响小）
缺口 2：resume 完成后不回写
  • append_turn / maybe_extract_memories / 输出脱敏都只在 run_question 里
  • revise 修正后的答案不进历史表（下一轮注入看不到修正版）、不进长期记忆、响应未脱敏
  • 修复方向：resume 端点复用 run_question 同款收尾
核心一句话：本系统有三层互不相同但哲学一致的「断点」——图执行靠 interrupt + checkpoint + Command(resume)（暂停点落库、恢复点续跑），定时任务靠 DB 状态 + APScheduler 同步 + 重启重放，多轮会话靠 thread_id 历史注入 + 指代改写 + token 压缩；恢复对话时 checkpoint 自足、无需查历史表，但「执行恢复自足 ≠ 应用层收尾自足」。
